# 复盘与学习

## 最难问题

难点是把模型建议与可授权执行区分开：模型即使输出 save_draft，也必须通过审核和确认守卫；保存工具即使被调用，也必须经过事务提交才算成功。将确认绑定到具体提案，防止占用变化后旧授权继续生效。

## 一次真实失败及修复

首轮真实模型 15 个场景中，missing 场景没有达到预期状态。工具补查没有找到新资料，却无条件清空此前的审核证据。模型根据“仍缺 title”调用 request_information 时被拒绝，随后重新审核后选择 block。

这不是模型发现了业务高风险，也没有发生越权保存；但结果把可补充资料的问题误标为阻断。保留完整失败 Trace：`examples/regressions/missing_before_fix.output.json`，首轮汇总：`examples/regressions/first_live_run.summary.json`。

修复：仅在资料发生变化时使审核过期；空补查保留既有缺失证据。进一步要求 missing_information/needs_review 通过 request_information 表达，并增加回归测试。随后重新运行真实模型验收，结果见评估文档。

## 技术取舍

- 不为框架名称增加依赖：原生工具协议已经足够展示模型选择和观察循环。
- 从 JSON 文件切换 SQLite：唯一约束和写事务能直接验证重复/并发，不依赖模型记忆。
- 暂不做 UI 和真实发布：优先完成审核、确认和保存这条高风险主链路。
- 显式保存失败记录：测试不是为了只展示成功，需要有可复查的 bad case 和修复证据。

## 时间与完成边界

实际耗时以仓库内本次开发工作记录为准；这是 AI 工具工作窗口，不等于候选人独立投入时间。未完成：候选人个人复核和数字题号填写；生产级语义审核、外部事务排期、身份认证审批、草稿取消/改期、部署和真实业务数据评估。

## 下一步

优先增加真实运营素材标注集与重复评估，验证模型在风险标签、冲突选择、工具故障上的稳定性。上线前补认证审批、版本化排期、失败重试策略和监控。面试时应能解释为何“最后一步已保存但循环未结束”同时报告 incomplete 和 saved，而不能丢弃事实。
